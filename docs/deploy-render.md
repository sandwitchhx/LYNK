# Deploy LYNK to Render

LYNK runs as one Node.js web service. The Blueprint in `render.yaml` configures Node 24, the existing `npm start` command, `/health`, and a persistent disk mounted at `/var/data`. SQLite and uploaded attachments are stored on that disk. A persistent disk requires a paid Render web-service plan and keeps this deployment to one instance, which matches LYNK's current SQLite and in-memory WebSocket presence design.

## Create the Render service

1. Push this repository to GitHub, GitLab, or Bitbucket.
2. In Render, choose **New → Blueprint**, connect the repository, and select the branch to deploy.
3. Render reads `render.yaml`. Confirm the web-service plan and persistent disk before creating the service.
4. Wait for the first deploy to become healthy. Render provides `PORT` and `RENDER_EXTERNAL_URL`; the app listens on `PORT` and uses the Render URL as its trusted WebSocket origin unless `CLIENT_URL` is set explicitly.
5. Open the service URL and confirm `/health` returns JSON with `"status":"ok"`.

If you use a custom domain, set `CLIENT_URL` to that exact HTTPS origin in the Render service's Environment page, then redeploy.

## Create the first admin account

The local SQLite database is ignored by Git, so the Render service starts with an empty database. To create an admin there:

1. In the Render service's **Environment** page, temporarily add:
   - `LYNK_BOOTSTRAP_ADMIN_NAME`
   - `LYNK_BOOTSTRAP_ADMIN_EMAIL`
   - `LYNK_BOOTSTRAP_ADMIN_PASSWORD` (at least 10 characters)
2. Save the variables and wait for the service to redeploy.
3. Open the service's Shell and run `npm run admin:create` once. The command hashes the password with bcrypt and creates an `ADMIN` user. If the email already belongs to an admin, it leaves that account unchanged; it never promotes another role.
4. Remove the three bootstrap variables from the Environment page and redeploy. The account and password hash remain on the persistent disk.

Do not add real passwords or the SQLite database to the repository. Student accounts, tickets, messages, notifications, and attachments created after deployment are stored on Render's disk.

## Moving existing local data

The new Render disk starts empty; it does not automatically copy `data/lynk.sqlite` or `data/uploads` from this computer. If existing tickets and accounts must be retained, stop the local app, make a SQLite-consistent backup, and transfer the database and uploads directory to `/var/data` before switching users to Render. Do not copy only the main SQLite file while the app is running because recent transactions may still be in the WAL file.

## Runtime notes

- The Blueprint creates one instance with a persistent disk. Do not scale this service horizontally: the SQLite database and active WebSocket/presence maps are local to that instance.
- Render supports inbound WebSocket connections. Connections can close during deploys or instance restarts; the client reconnects and synchronizes messages from SQLite.
- Back up both `/var/data/lynk.sqlite` and `/var/data/uploads`. Losing either can affect account/ticket data or attachment availability.
- `JWT_SECRET` is generated by Render and must remain stable across deploys so existing session tokens remain valid.
